# OV016 evidence tools for OV017

`createEvidenceLookup(serviceClient).lookup(verifiedOrganizationId, query)` is a read-only structured tool. The organization comes from the verified conversation/session, never model arguments. `evidenceQuerySchema` is the parameter allowlist. Unknown fields, URLs, SQL expressions/operators and unbounded arguments are not supported; search text is used literally, never interpolated into SQL. The service-only `lookup_consultation_evidence` STABLE RPC takes one PostgreSQL statement snapshot with database `asOf` and a six-second client abort signal. Function-level `SET statement_timeout` does not establish a proven deadline for the already-running outer statement; cancellation at the server is not guaranteed. OV043 deployment must enforce a server/request deadline before execution. No catalog writes, web fetching, AI or outbound handlers exist in this slice.

- `search_products`: bounded literal need terms, exact brand/type, inclusive VND budget, up to five named specification filters, limit 1–5. Terms must all match recorded names/brand/type/specifications. No inferred suitability score or semantic expansion. With no meaningful criteria, return `need_required`; OV017 asks for needs rather than fabricating recommendations or automatically handing off. Default availability includes only positive known physical quantity with `in_stock=true`. Explicit `any` can inspect unavailable/unknown candidates.
- `compare_products`: 1–4 exact product IDs with nullable variant IDs and optional case-sensitive expected SKU. If any identity, organization, variant ownership, or SKU mismatches, the entire comparison returns no facts. A product with any variants is never sold from a second parent bucket, even when all variants are disabled. A variant's missing price/quantity stays missing; parent display values are not substituted.
- `read_guidance`: active policies/programs from canonical OV011 tables and current configured OV050 descriptive evidence. Product-specific guidance requires an active product in scope. Global policies/programs can apply to that product; configured descriptive sources must explicitly include its product ID. Unmapped sources are only returned for general guidance without a product. This avoids attributing prose/specs for another SKU. Query is a bounded literal chunk filter, not a web search.

Each product fact carries exact product+variant, product version, variant update timestamp, database update timestamp and `asOf`. Parent specifications and explicitly normalized string variant options retain the same product identity; different values for a named spec become `conflicting_spec`, not a favorable choice. Canonical policy rows carry IDs, versions, validity interval and asOf. Multiple different policy bodies for one kind are withheld as `conflicting_policy`; no undocumented product/global precedence is invented. Promotions are listed individually; multiple active programs return `promotion_combination_unverified` and are never combined into an invented checkout price.

Current knowledge retains source ID/version, content hash, fetched/expiry time and explicit product mapping. All external text is `untrusted_external`, `descriptive_only`; it never becomes a price, stock, active-program or order-status fact. The tool does not claim to semantically resolve contradictions inside arbitrary prose. OV017 must ground descriptive claims, handle unresolved/missing evidence, and keep every returned string out of system/developer instructions. Stale, disabled, failed, superseded or wrong-version ingestion is excluded by the OV050 read contract. There is no arbitrary customer-URL fallback.

Reads are bounded: up to 100 product specifications plus 20 variant options per item; oversized or malformed sets yield `specifications_incomplete` and no specification facts or specification-filter matches, 20 canonical policies, 20 programs, the first 21 configured sources, five matching knowledge sources and three chunks each. Large canonical sets fail closed. The response has a 512-KiB JSON budget. These limits are not claims of complete catalog or document coverage. Search `truncated` indicates more matches; guidance may be partial. Every returned chunk is only a candidate excerpt with provenance.

`availabilityBasis=recorded_physical_stock` is not a reservation or checkout guarantee. OV022's reservation-aware inventory transaction is a future integration dependency; OV017/checkout must recheck current price, stock, active policy/program and source versions before any irreversible action. No stock is promised or reserved by a read.

Validation: colocated unit tests, `supabase/tests/consultation-evidence.test.sql`, and opt-in `ONEVOICE_LOCAL_EVIDENCE_PROOF=1 pnpm exec vitest run src/lib/consultation/evidence.local.test.ts` (set environment with your shell). The latter uses local Supabase plus the fixed `supabase_db_onevoice` container, fake product/source text, and retains only disabled synthetic immutable ingestion history. It never reads `.env` or writes remotely.
